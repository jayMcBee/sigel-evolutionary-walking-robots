# xtest-baseline.txt -- what the port does with REAL X INPUT.
#
# The values are the port's for twoBases.exp. build-fast/guidrive runs as a
# normal X11 client inside a
# nested Xvfb, 1400x1000x24, with no window manager, under
# QT_QPA_PLATFORM=xcb. xdotool sends XTEST input. check.sh's `real clicks'
# section reproduces this file. Lines starting with # are stripped before the
# diff.
#
# WHY THIS FILE EXISTS
# Every other behavioural baseline here was captured with QTest. QTest builds a
# QMouseEvent and gives it to QApplication::notify. That runs every slot SIGEL
# has, but it never goes through QWindowSystemInterface. So it cannot test
# window activation, the pointer grab a popup takes, or Qt's synthesis of a
# double click from two presses. PORTING.md's C10 section named those and said
# no tool on this machine could deliver a real click. That was measured on the
# live Wayland session only, and it was too broad. In a nested plain X server
# there is no compositor and no vmware-user owning the pointer, and XTEST is
# ordinary. This file is the result.
#
# THE CONTROL IS IN THE OUTPUT
# It is in the `-- 2. provenance --' block. check.sh fails the section if the
# word DISCRIMINATES is missing. The scenario compares one real XTEST click
# against one QTest::mouseClick at the same point, through a native event
# filter. The real click produces native ButtonPress events and reaches
# QWidgetWindow before the QWidget. The QTest click produces no native event and
# never touches QWidgetWindow. Without that line, every count in this file is
# also consistent with nothing having been clicked.
#
# QEvent::spontaneous() CANNOT BE THAT CONTROL
# Qt's own qtestmouse.h calls QSpontaneKeyEvent::setSpontaneous() on the event
# it posts, and only then calls qApp->notify(). A QTest click therefore reports
# spontaneous()==true, exactly like a real one. A probe built on it would pass
# with no real click in it.
#
# NUMBERS IN HERE THAT ARE NOT ONE PER CLICK. All measured, none assumed:
#   native press=2 for ONE click   Qt's xcb plugin uses XInput 2. The master and
#                                  the slave device both report.
#   qt press=2 for ONE click       QWidgetWindow first, then the QWidget.
#   qt enter=8 for one crossing    One Enter per widget in the nested stack
#                                  under the pointer.
#   Section 4 prints NO pixel coordinates and no popup rectangle. Those come
#   from the local font and style: under QT_STYLE_OVERRIDE=Windows the File
#   popup is 228x235 instead of 261x214, which moves both the rectangle and the
#   point a geometry search would pick. The outside point is list ROW 3, by
#   index, the same row the oracle used on 1.3.
#   nativeEnter/nativeLeave = 0 in section 6. This is correct. X sends crossing
#                                  events per X window. A Qt 6 top level is one
#                                  X window. Moving between widgets inside it
#                                  crosses no X boundary. Qt works out those
#                                  Enter and Leave events itself.
#
# TWO DIFFERENCES FROM 1.3 ARE PINNED HERE. Both are in Qt's popup handling.
# Neither is in SIGEL's code. The oracle measured 1.3 on the 2003 binary with
# real XTest on 2026-09-07. PORTING.md's C13 section has both in full.
#   1. A click that closes an open menu is swallowed here and passed on by 1.3.
#      On 1.3 one click closes the File menu and selects the row under it. Here
#      the row does not move and a second click is needed. THE CONTROL LINE
#      BELOW IT IS WHAT MAKES THAT A FINDING: the same click, at the same point,
#      with no menu open, does select the row. So the target is right and the
#      click really is being eaten.
#   2. A second click on the same menubar item closes the menu here. On 1.3 it
#      stays open.
# If either line changes, the port's popup behaviour has moved. Do not edit this
# file to make the diff go away. That is the finding.
#
# X INPUT FOCUS IS NAMED, NEVER PRINTED AS AN ID. Window ids are assigned per
# run, so the number would differ from itself every time. The name comes from
# xdpyinfo, not from `xdotool getwindowfocus': on an idle nested server xdotool
# exits 1 and prints nothing, and reading that as "None" would report
# PointerRoot(1), a real None(0) and any xdotool failure with the same word.
# 1.3 keeps focus on the root window at rest, moves it to the popup while a menu
# is open, and leaves it at None after an outside click. Qt 6 here holds the
# main window throughout, because the port claims focus during startup. That is
# the toolkit, not the port logic. It is recorded, not judged.
#
# SECTION 3 SAMPLES TOO LATE TO SEE ACTIVATION. Both of its samples read
# isActiveWindow=1, because the port activated the window during startup. It
# records a settled state, not a change. Activation does happen: section 2 shows
# act=1 on the first real click, and a run in which no click lands reports
# isActiveWindow=0 throughout. A session that adds a window manager to the
# nested display should expect section 3 to move.
#
# THE SCENARIO REFUSES A SCALED DISPLAY. Widget coordinates are logical pixels
# and xdotool takes device pixels. At devicePixelRatio 1.25 the clicks are real
# but land 20 per cent away, and the run reports a false difference from 1.3.
# check.sh clears the scaling variables and the scenario refuses any ratio other
# than 1.
# The native motion count is printed as motion>0, and the XInput2 total
# excludes motion. The X server sends a spare motion event under load, which
# failed this check twice on lines whose Qt-level counts were all identical.
