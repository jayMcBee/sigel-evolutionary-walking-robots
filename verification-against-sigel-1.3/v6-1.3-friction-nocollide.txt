============================================================================
Captured 2026-08-29 on the x86 reference box, through the sigel-x86 session.
One run on hammerNiceWalkingFitness.exp. V7 covers the remaining rules.

SUBJECT
-------
D10 converted SIG_Link::noCollide and D11 SIG_Material::friction. No shipped
file exercises either, so this is the only external check on both.

hammer loads materials plastic, metal, rubber and links base, hammer,
middle1, middle2, middle3. rubber is last, so metal is loaded before it.
base is first, so it is loaded before middle1. The parser drops a partner
that is not yet loaded (V7 result 2), so both edits name a loaded partner.

METHOD
------
Scratch copy. The pristine hammer was md5-verified unchanged afterwards. The
two dead 2003 roots were repointed separately -- /home/pg368/sawitzki/sigel,
and /home/pg368/sawitzki/hammer/ on the three Body lines, all of which sit
inside the StreamedRobot block that opens at line 75243. Each edit asserted
the expected token before substituting it. No pvmd, so the run is a pure load
and save with zero generations evaluated.

  wrote  Material rubber 1 1 0 1 0 0     -> Material rubber 1 1 1 metal 0.25 1 0 0
  wrote  Link middle1 ... t[28] == '0'   -> ... 1 base ...

PREDICTION, MADE BEFORE THE RUN
-------------------------------
Both setters negotiate by default, so the partner gains the reverse entry and
the saved file shows pairs on both sides.

MATERIAL ORDER PERMUTED ON THE ROUND TRIP
-----------------------------------------
  in:   plastic metal rubber
  out:  plastic rubber metal

The Link lines did not move. V8 result 3 repeats this on an unedited file, so
the edit did not cause it.

OUR BUILD EMITS plastic, metal, rubber. This is a real difference from 1.3.
The shim-era baseline (5ebc9a8:dictorder-baseline.txt) has plastic, rubber,
metal, so the old build matched and D3's flip to insertion order moved us off
it. See PORTING.md V6 RESULT.

Results are reported per named entity, never by position.

ALSO OBSERVED
-------------
nfric and the pair list are written for BOTH partners, so one declared pair
costs two entries on save. A serialiser writing only from the declaring side
would make a round-tripped file appear to gain an entry that is really just
negotiation. Ours writes both.
