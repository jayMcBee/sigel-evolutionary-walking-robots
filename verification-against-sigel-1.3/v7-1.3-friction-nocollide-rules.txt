V7 -- friction and no-collide rules, from the SIGEL 1.3 binary
=============================================================
Captured 2026-08-29 on the x86 reference box, through the sigel-x86 session.
Four runs on walkerNiceWalkingFitness.exp. V6 covered hammer.

SUBJECT
-------
walker has 4 materials and 19 links. Load order:

  materials  footMaterial legMaterial bodyMaterial shoulderMaterial
  links      shoulder5 body shoulder6 foot1..foot6 leg1..leg6 shoulder1..shoulder4

Runs declared two partners wherever the format allows, so the inner lists are
exercised as containers.

METHOD
------
Scratch copies. The pristine walker was md5-verified unchanged after each run.
The two dead 2003 roots were repointed separately. Each edit asserted the
expected token before substituting it. No pvmd, so each run is a pure load and
save with zero generations evaluated.

Results are keyed to named entities. The containers permute on a round trip
(V1), so a position is not a key.

RESULT 1 -- multiple partners work, each keeping its own value
--------------------------------------------------------------
  wrote  shoulderMaterial -> footMaterial 0.3 bodyMaterial 0.7
  got    footMaterial  nfric 1  shoulderMaterial 0.3
         bodyMaterial  nfric 1  shoulderMaterial 0.7
         legMaterial   nfric 0

Not swapped, not averaged. Pair order preserved.

RESULT 2 -- a partner not yet loaded is dropped, with no message
----------------------------------------------------------------
  wrote  body -> foot1 leg1        got  body nNoCollide 0   both lost
  wrote  leg1 -> body              got  kept
  wrote  shoulder4 -> body foot1   got  both kept

body is the second link loaded, so foot1 and leg1 are forward references. No
warning, no error, exit 0. The rule is "partner already loaded", not "one
partner only". Negotiation itself is not order-limited: the reverse entry is
installed into a link parsed before the declaration existed.

RESULT 3 -- a duplicate partner is refused, on both sides
----------------------------------------------------------
  wrote  footMaterial 0.3 footMaterial 0.7   got  nfric 1, value 0.7
  wrote  body body                           got  nNoCollide 1

The second declaration updates the first; last wins. The negotiated reverse
entry is de-duplicated too -- body came back with one entry, not two. This is
the behaviour D10 and D11 converted: D10's containsRef(x)==0 -> !contains(x),
D11's append-versus-update walk. Both are upstream.

RESULT 4 -- a dropped forward reference is not resurrected
-----------------------------------------------------------
  wrote  bodyMaterial     (3rd) -> shoulderMaterial 0.3   forward, dropped
  wrote  shoulderMaterial (4th) -> bodyMaterial 0.7       valid, negotiates
  got    bodyMaterial  nfric 1  shoulderMaterial 0.7

The pair is present, the partner name is right, nfric is right and the graph
is symmetric. The value is the other side's. The 0.3 is gone, no warning,
exit 0. nfric is 1 and not 2, so the reverse entry is a fresh insertion, not a
repair. Nothing records the discarded declaration. A count check cannot see
this; only a value check can.

CONSEQUENCE
-----------
Once friction or no-collide entries exist, emission order decides which
entries survive a load. A permutation that moves a partner after its declaring
entity drops that entry, and negotiation then refills it with the other side's
value. Nothing shipped declares either, so this is latent. It bears on
PORTING.md section 10's choice of iteration order over numbering for .rrb.
