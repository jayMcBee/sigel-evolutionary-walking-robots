WHAT BOUNDS A VALUE-LEVEL PROBE, AND WHY THE FORCE HALF CANNOT BE BIT-COMPARED
    This machine is aarch64 and its `long double' is IEEE binary128. 1.3's i386
    `long double' is the x87 80-bit format. Measured here: LDBL_MANT_DIG == 113
    against 64 for x87.

    DO NOT USE sizeof, AND DO NOT USE THE ROUNDING TEST. An earlier version of
    this file cited sizeof(long double) == 16 and
    (double)(3.14159265L/180.0L) != 3.14159265/180.0. Neither discriminates,
    and the oracle demonstrated it by running both on x86-64: sizeof is 16
    there too, because the 80-bit x87 value is padded to 16 bytes, and the
    inequality holds there too, because it only says "compute in any extended
    precision, then round, and you differ from computing in double". Both
    results appear on a machine whose long double format is IDENTICAL to 1.3's.
    LDBL_MANT_DIG is the quantity that tells the formats apart: 64 for i386 and
    x86-64 x87, 113 for aarch64 binary128.

    AND THIS IS A PROPERTY OF THE BUILD HOST, NOT OF THE PORT. Do not read it
    as "the force path can never be verified". A build on x86-64 would give a
    long double bit-identical in FORMAT to 1.3's, and moveDrive would become
    comparable. That would still not close the plain-`double' gap: x86-64
    computes double in SSE at a true 64 bits, where i386 used x87 with 80-bit
    intermediates, so full closure would additionally need -mfpmath=387.
    An x86-64 build buys the long double half only.
    moveDrive carries its VALUE CHAIN in long double -- minRegisterValue,
    registerValueRange, absoluteRegisterValue, sigelDestAngle, destAngle,
    dmDestAngle and force. Not everything in it is long double: q, qd, intMin,
    intMax and jointInput are plain double, and intMin is added back at
    CommandInterface.cpp:174. But the quantities the command computes cross the
    precision boundary, so they CANNOT be compared bit for bit between the two
    machines. That is D26 and section 7's x87/IEEE boundary, not a port defect.
    sense is comparable further: scaledState and posRange are plain double all
    the way to the divide. Its register-value steps then mix double with long
    double -- Queries.cpp:151 in the joint branch, :209 in pitch/roll and :261
    in the third -- and cross the same boundary.
    So a future value probe should stop at scaledState, not at registerValue.
