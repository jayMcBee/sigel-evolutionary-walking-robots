V8 — the GP parameter blocks, captured BEFORE the conversion
=============================================================
Captured 2026-08-29 on the x86 reference box, through the sigel-x86 session.
Captured BEFORE the conversion it serves, so it cannot be tuned to agree.

WHY, AND WHY NOW
----------------
The container shim is out of all simulation code. What remains is 51 places in
SIGEL_GP, MT_Control and MT_GPSystem. Two of those run on EVERY test:

    SIG_GPParameter::hostList          Q2PtrList, filled from PVMHOST lines
    SIG_GPExperiment::experimentHistory Q2PtrList, filled from HISTORY blocks

sigel_eval builds a whole SIG_GPExperiment, so both are exercised by both
gates. Both write their order into the saved .exp. Both are next to convert.

METHOD
------
hammerNiceWalkingFitness.exp, UNMODIFIED except the two dead 2003 roots.
No content edits. Loaded and saved three times in succession; the repetition
is what exposed result 2. Scratch copy, pristine md5-verified afterwards.

    host01 host02 host03 host04 host05 host06 host07 host08 host09 host10
    host11 host12 host13 host14 host15 host16 host17 host18 host19 host20

RESULT 2 — HISTORY BLOCKS GROW 7 BYTES PER SAVE, WITHOUT LIMIT.
---------------------------------------------------------------
Count and position are preserved: 100 blocks in, 100 out, every pass, and the
individual NAME sequence is byte-identical. So the population container does
not reorder and block n still belongs to individual n.

The CONTENT is not stable. First block, successive passes:

    input   10574 chars     file 1553928 bytes
    pass 1  10581           file 1554783
    pass 2  10588           file 1555483
    pass 3  10595           file 1556183

+7 characters per block per save. The appended text is exactly "\n      " --
a newline and six spaces. The preceding 10574 characters are byte-identical,
so nothing is rewritten; it is a pure append. At 100 blocks that is ~700 bytes
per round trip, linear and unbounded.

IT IS ONE WHOLE LINE, not merely 7 bytes, because the appended text starts
with a newline. Each block gains a whitespace-only line per save. Visible in
the section marker offsets, which shift by exactly +100 lines per pass across
100 individuals:

    input   #####  at 37 65 190 75242 75329 75491
    pass 1         at 37 82 209 75363 75450 75612
    pass 2         at 37 82 209 75463 75550 75712
    pass 3         at 37 82 209 75563 75650 75812

A line-shaped defect is what breaks a readLine() loop, which is why this
matters.

The growth is UNIFORM. Counting lines between HISTORY BEGIN{ and
}HISTORY END; per block, input against pass 1: all 100 blocks gain exactly
one line, none gains two. One line per individual per save.

    per-block growth: Counter({1: 100})

A first reading of the marker offsets gave "+100 per pass" for every pass.
Pass 1 is +121. Full per-section decomposition, which closes it:

    section          input    pass1    pass2    pass3    p1-in  p2-p1  p3-p2
    s1 (pre-#1)         36       36       36       36        0      0      0
    s2                  27       44       44       44       17      0      0
    s3                 124      126      126      126        2      0      0
    s4 population    75051    75153    75253    75353      102    100    100
    s5                  86       86       86       86        0      0      0
    s6 exp-history     161      161      161      161        0      0      0
    TOTAL            75485    75606    75706    75806      121    100    100

Section 4's 102 is 100 history lines plus 2 one-off. Passes 2 and 3 are +100,
all of it history. The appended line lands at the END of each block, immediately before
}HISTORY END;, so nothing is stranded behind it. The second and third markers
also move once, 65->82 and 190->209, then never again -- the one-off reshaping
from the first save.

CAUSE, found on our side afterwards -- SIG_GPIndividual.cpp:

    write  :557   file << "\n      HISTORY BEGIN{";
           :558   file << history.join("\n");
           :559   file << "\n      }HISTORY END;";

    read   :647   histStr = indStr.mid(pos+14,
                      indStr.indexOf("}HISTORY END", pos+15) - pos - 14);
           :648   history.append(histStr);

The reader takes everything between "HISTORY BEGIN{" and "}HISTORY END" --
which INCLUDES the "\n      " the writer emitted before the closing marker.
The writer's own separator is read back as content, then written again with a
fresh separator. Hence +7 per save.

OURS IS THE SAME CODE AND HAS THE SAME DEFECT. Upstream, not a port
regression. NOT FIXED: changing it would change file bytes against 1.3, and
the port's rule is to preserve behaviour. Recorded in PORTING.md section 9.

CONSEQUENCE: a gate that diffs a round-tripped file against a reference will
differ on every run even when the containers are perfect, and the difference
will grow each time. Any such gate must normalise trailing whitespace inside
HISTORY blocks first. V1's involution finding is about container ORDER and
still holds exactly; history CONTENT is outside it and only ever grows.

RESULT 4 -- the EXPERIMENT history is byte-stable
-------------------------------------------------
A second, different history lives in the same file: the sixth and last #####
section, one line per generation, held by SIG_GPExperiment::experimentHistory.
It is a different container from the per-individual HISTORY blocks above.

    input   161 lines / 160 entries
    pass 1  161 / 160     generation numbers 1..160, in order
    pass 2  161 / 160     same
    pass 3  161 / 160     same

Byte-identical: same md5 for the whole section in the input and all three
passes. First and last entries unchanged:

    1 2001 8 8 21 13 32 0.0821164 0 0.00939138
    160 2001 8 9 7 30 45 0.45972 0 0.3833

(single-spaced, as in the file -- an earlier draft column-aligned these inside
a paragraph asserting byte-identity, which is exactly the wrong place to
re-space a quotation)

So it behaves as a plain appending list. Order and count preserved, contents
stable under repeated save, and the growth defect in result 2 does not reach
it.

The section holds exactly ONE blank line, the last, between entry 160 and the
closing #####. It is in the pristine input too, so it is part of the format
rather than something a save introduces, and it does not multiply. The reader
loops "while (!buffer.isEmpty())" over readLine(), so it terminates there and
no entry is ever behind it. Nothing can silently truncate the list.

Captured before D14 converted the container.

RESULT 5 -- THE FIRST SAVE IS A FORMAT UPGRADE
----------------------------------------------
The shipped .exp are a 2001-era format revision. The 2003 binary writes ten
keys they predate, adding them with defaults on the FIRST save and then
holding steady. This is what the 21 non-history lines of pass-1 growth are:

    s2, 17 lines, eight keys
        FLOORDIMENSION / 50 / 50      FLOORFUNCTION / 0
        FLOORPICTUREFILE / <blank>    FLOORFUNCSELECTED / 1
        TEXTUREFILE / <blank>         TEXALPHA / 255
        WITHTEXTURE / 0               AUTOSAVETIME / 0
    s3, 2 lines    RESEVGEN / 0
    s4, 2 lines    WITHHISTORY / 1, at the top of the section

WITHHISTORY is absent from all twelve shipped experiments, is added on first
save, and stays at exactly one occurrence through passes 2 and 3. The same
holds for the other nine.

CONSEQUENCE FOR ANY ROUND-TRIP GATE, INCLUDING V2
-------------------------------------------------
A round trip of any shipped .exp differs from its input by those ten keys on
the first save, no matter how correct the port is. A gate that compares a
shipped file against its own round trip WILL FAIL, and will be right to.

Compare pass 1 against pass 2, not input against pass 1 -- or expect the ten
additions explicitly. Note also that the per-individual history grows one line
per block per save even between passes 2 and 3, so a pass-1-vs-pass-2 gate
must still normalise trailing whitespace inside HISTORY blocks (result 2).

The only parts stable from the input onward are the ones measured above:
PVMHOST order, experiment-history contents, and section 6 as a whole.

WHICH PATH RESULTS 1 TO 5 CAME FROM IS NOT RECORDED. This file's METHOD says
only "loaded and saved three times in succession". Result 5's 255 therefore
identifies that capture as the headless path by its VALUE, now that both
values are known -- it is not a claim about how it was run.

CAUSE, in 1.3's own source and Qt 2's. SIG_Environment.cpp:47 defaults texAlpha
to 0xFF. SIG_EnvironmentView.cpp:180 pushes it into sliderAlpha on load, and
:112 reads it back on save. The pristine form gives that slider a name and an
orientation and nothing else, no maximum -- read it with

    git show 0516d62:x/kdesigelSources.1.3/kdesigel/kdesigel/ui/SIGEL_MasterUI/SIG_EnvironmentBase.ui

because the file at that path today is the CONVERTED Qt 4 form. Qt 2's
QRangeControl() sets maxVal to 99 (qrangecontrol.cpp:111-119) and
QSlider(Orientation,...) uses that default constructor (qslider.cpp:124). Qt 6
has no QRangeControl at all; its 0-99 default comes from QAbstractSlider.
The headless path has no slider and keeps 255.

SAME NUMBER, DIFFERENT MECHANISM -- AND THAT IS WEAKER THAN IT LOOKS. The two
99s do not share a code path. 1.3's comes from Qt 2's QRangeControl default;
ours comes from Qt 6's QAbstractSlider default. They agree on the value today,
and nothing enforces that they keep agreeing. A Qt release that changed the
default would move our side alone, silently, and the gate would then be the
only thing that noticed. Do not read "the port is faithful here" as "the port
cannot drift here". If it ever moves, the fix is to set the maximum on the
form explicitly rather than to chase the toolkit.

NOT MEASURED: that 1.3's Alpha slider really reports a maximum of 99. The
oracle attempted it, the nested X server went down mid-probe, and the reading
was not retaken. What is established is the two file values above and the Qt 2
source. The clamp is the explanation for them, not an observation of its own.

CONSEQUENCE: pick the reference by PATH. A GUI save must be compared against a
GUI capture. Every other line agrees between the two paths, which is why the
V2 gate can compare our GUI save against this headless capture -- but that is
a measured licence, not an assumption.
